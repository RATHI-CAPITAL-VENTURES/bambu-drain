# Retro — 0.3.0, health that reaches you (2026-09-01)

**Scope:** `feat/health-push`. A health verdict computed on the Pi, pushed to the
Mac, so RIA can alert on it without touching the LAN.

## What went well

- **The constraint picked the architecture.** RIA cannot reach the Pi — macOS
  Local Network Privacy blocks her launchd server from the LAN, the same thing
  that broke the lamp and Radarr. Rather than fight that, the Pi pushes and RIA
  reads a local file. No new credentials, no LAN access, no LNP grant, and it
  reuses the SSH link the ship loop already owns.
- **One definition of healthy.** The verdict is computed on the Pi and read
  verbatim by everything else. RIA cannot import `bambu_drain`, so the
  alternative was reimplementing the rules in a second language in a second
  repo, where they would silently drift.
- **Designing for the watch shaped the output.** RIA's job runner fires only when
  a checker's stdout *changes*, which forced the verdict to be stable during
  healthy operation. That turned out to be a good property independent of the
  watch, and there is now a test asserting that idle seconds and file counts
  cannot move it.

## What was hard to understand

- **Which end can detect staleness.** A stalled loop cannot report that it is
  stalled, and a stale file pushes exactly as well as a fresh one. The split is
  now explicit in the module docstring: the Pi computes everything it can see,
  and the *reader* compares the file's `ts` to now. That single reader-side check
  covers the Pi being dead, the network being down, and the push itself failing,
  without any of them needing to report themselves.
- **`--verdict` returning a non-zero exit status is correct and surprising.** It
  makes the command usable in a shell test, and it aborted a `set -e` deploy
  script mid-run the first time it went unhealthy.

## Gaps found

| Gap | Kind (docs / testing / process / observability) | Follow-up | Status |
| --- | --- | --- | --- |
| The daemons never wrote `status.json` — only a human running `status` did, so its timestamp meant "last time someone looked" | observability | code | landed here — the drain loop writes it every pass, making the file's age the loop heartbeat |
| `sudo bambu-drain <anything>` failed with `No module named bambu_drain`; the wrapper relied on an EnvironmentFile only systemd reads | correctness | code | landed here — the wrapper sets `PYTHONPATH` itself |
| Integrity events had no time bound, so one incident alarmed forever | observability | code+test | landed here — bounded to one hour, with boundary tests |
| The verdict could have been made to move during healthy operation, which would make a change-detecting watch fire constantly | testing | test | landed here — a test asserts idle seconds and file counts do not move it |
| Nothing verifies the alert path end to end — that a real fault actually produces a text | testing | test | blocked: needs a fault injected on live hardware while the RIA job is armed; the verdict logic is unit-tested but the delivery path is not |

## Follow-ups landed in this milestone

- The status file is now written by the process that knows, at the rate that
  matters, instead of as a side effect of someone looking.
- Every `sudo bambu-drain …` line in the README, SETUP and TROUBLESHOOTING docs
  now actually runs. They were written from the long
  `PYTHONPATH=… python3 -m …` form used during development and never tested in
  the form they were published in.

## Follow-ups blocked (and why)

- **End-to-end alert verification.** The verdict logic has unit tests for every
  failure mode, and the push is verified live. What is untested is the whole
  chain: a real fault on the Pi producing a text on the phone. That needs a
  deliberate fault injected on live hardware with the RIA job armed, which is
  worth doing once the job has been running long enough to trust its cadence.
