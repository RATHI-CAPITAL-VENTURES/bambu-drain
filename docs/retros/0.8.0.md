# Retro — 0.8.0, the parts worth watching (2026-09-03)

**Scope:** `feat/timelapse-bookends`. Real-time clips at the start and end of a
reconstructed timelapse, plus a fix to the frame estimate.

## What went well

- **The feedback was better than the metric.** The render was working exactly as
  designed — 60 seconds, right frame count, correct sampling — and the result
  was unsatisfying, because at one frame per ~9 seconds of print the levelling,
  the purge and the first layer occupy about 0.2 seconds. Nothing in the code
  was wrong. It took someone watching it to notice.
- **The fix is what real timelapses do.** Bookending with normal-speed clips is
  a convention rather than an invention, and it cost three encode passes and a
  concat.

## What was hard to understand

- **I diagnosed a bug that did not exist.** The first bookended render came out
  at 624 frames against an expected ~915, and I spent three rounds hunting a
  fault in the concat — testing head and tail in isolation, comparing stream
  parameters, recounting frames. The concat had been right the whole time:
  150 + 323 + 151 = 624 exactly. My *expectation* was wrong, because I had taken
  the body's estimated frame count as its real one.

  The lesson is narrow and worth keeping: when a computed number disagrees with
  an expected one, check the expectation with the same rigour as the code. I
  verified every component of the pipeline before questioning my own arithmetic.

- **The estimate that misled me was also genuinely wrong**, just far less than I
  thought. `plan()` extrapolates keyframe density from the first segment across
  all of them, but the last segment of a print is always short — that is how the
  ending is detected in the first place. Across twenty segments that is a
  rounding error. Across two it is 50%, which is precisely the case I tested.

## Gaps found

| Gap | Kind (docs / testing / process / observability) | Follow-up | Status |
| --- | --- | --- | --- |
| The start and end of a print were compressed to ~0.2 s and effectively invisible | correctness | code+test | landed here — `head_seconds` / `tail_seconds`, real-time bookends |
| `plan()` counted the short final segment as full, so the body ran short | correctness | code+test | landed here — the last segment counts as half, with a test naming the two- and twenty-segment cases |
| A test asserted a two-segment render should reach 60 s, which the footage cannot supply | testing | test | landed here — it now asserts the floor behaviour instead: sample every keyframe, output what exists |
| Bookend length is fixed at 5 s regardless of print duration | docs | — | blocked: no evidence yet that a 4-hour print wants a different opening than a 20-minute one. Configurable, and worth revisiting only if it turns out to matter |

## Follow-ups landed in this milestone

- The timelapse now shows the two moments people actually look for.
- The frame estimate accounts for the short final segment, so a requested length
  is met rather than undershot.

## Follow-ups blocked (and why)

- **Scaling the bookends with print length.** Both are configurable and 5 s is a
  guess that looked right on one print. Changing it now would be tuning against
  a single observation.
