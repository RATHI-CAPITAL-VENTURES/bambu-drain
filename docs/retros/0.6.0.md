# Retro — 0.6.0, prints named after their model (2026-09-03)

**Scope:** `feat/name-prints-after-model`. The sliced file opens and names a
print, and everything about that print lives in one folder.

## What went well

- **The start marker was hiding in plain sight.** Every signal until now could
  only say a print had *ended* — a short segment, a timelapse. The `.gcode.3mf`
  lands when the job is sent, ~15 minutes before the first chamber segment, so
  it says a print is *beginning*. It had been sitting in `models/` the whole
  time, filed away from the prints it belonged to.
- **Trace-then-decide beat guess-then-fix.** Two sessions looked wrong in the
  dry run. Rather than adjust thresholds, printing every file with its
  classification and its size as a percentage of the rotation size made both
  causes obvious in one screen — and neither was the threshold.

## What was hard to understand

- **The tool was eating its own output.** `timelapse-reconstructed.mp4`, a 169 MB
  file this project generates, sat in a print folder and classified as a chamber
  segment. At 70% of the rotation size that reads as a print ending, so it split
  one print in two. A migration that reclassifies its own output produces
  different results on the second run than the first, which is the worst
  property a migration can have.
- **Two closers in a row are one print, not two.** A print's last segment and its
  timelapse are flushed in the same second and *both* end a session. Whichever
  sorted first closed the print; the other opened a session containing only
  itself. The symptom was a scattering of one-file folders that looked like a
  threshold problem and was not.

## Follow-ups landed in this milestone

- One implementation of the naming and sizing rules, imported by the migration
  rather than copied into it. The copy had already drifted.
- Generated outputs are excluded from reclassification, so the migration is
  idempotent in the way a migration has to be.

## Follow-ups blocked (and why)

- **Naming the other half of prints.** When the Studio project is unnamed the
  sent file is called after the process preset — `0.2mm layer, 2 walls, 15%
  infill` — and a sliced `.gcode.3mf` has had its mesh objects stripped, so
  there is no model name inside it either. The only fix available to the user is
  to save the Studio project with a name before sending. Detected and documented
  rather than guessed at.
