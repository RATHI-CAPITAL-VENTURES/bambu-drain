# Retro — 0.4.0, one folder per print (2026-09-02)

**Scope:** `feat/group-by-print`. Per-print archive grouping, a configurable
archive folder name, and a migration for what was already archived.

## What went well

- **The dry run earned its keep immediately.** `regroup_archive.py` defaults to
  printing its plan, and the plan is grouped by session with file counts and time
  spans. That format is what made the bug visible: two sessions where there
  should have been three, one of them "spanning 4.8h" and holding a timelapse
  that obviously did not belong to it.
- **The fix came from the user knowing his own prints.** No test and no amount of
  reading would have caught it — the archive looked perfectly plausible. What
  caught it was "my most recent print has no timelapse, and that one is from a
  failed print I had to redo."

## What was hard to understand

- **The signal that looked sufficient wasn't, and the data proves it can't be.**
  Grouping by time gap seemed safe: measured within-print gaps were 9–18 minutes
  against 805 between prints. Then a failed print and its redo turned up **26
  minutes** apart. Separating those by time needs a ~22-minute threshold, four
  minutes above normal, which would fragment any print with a slow layer. There
  is no correct threshold. The timelapse is the only reliable boundary, and it
  was sitting in the data the whole time — I had even written it down as an
  option and then not implemented it.
- **A migration that renames files destroys its own re-run signal.** The first
  pass renamed `video_<ts>.mp4` to `timelapse.mp4`. When the closer logic was
  added, the script no longer recognised its own output, so re-running would
  silently lose every session boundary. It now matches both spellings.

## Follow-ups landed in this milestone

- The archive folder name is a choice again, not a hardcoded `BambuArchive` — it
  always was `ship.dest`, but the example and every doc implied otherwise.
- Config edits are section-aware and assert their resolved values. Patching by
  key alone silently corrupted a rule, and "it parses" hid it.

## Follow-ups blocked (and why)

- **Why the 4-hour print has no timelapse.** Verified that nothing was lost:
  the stick is empty, and only two timelapse videos exist in the whole ledger,
  both belonging to other prints. The printer simply never wrote one. The two
  candidates are a per-job setting that was off when the failed job was re-sent,
  or the save location having reverted to Internal. **The second matters** — it
  would mean this project silently misses the file it exists to capture — and
  telling them apart needs a look in Handy at internal storage.

- **Two consecutive timelapse-less prints.** The heuristic merges them, and no
  amount of parsing recovers what the printer never wrote. The honest options are
  a wider gap (fragments long prints) or asking the printer over the network
  (costs the cloud, which is the whole premise). Documented as a known limit.
