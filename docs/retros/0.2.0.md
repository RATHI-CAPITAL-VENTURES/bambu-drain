# Retro — 0.2.0, first working implementation (2026-08-31)

**Scope:** `feat/gadget-drain-loops`. The whole thing: gadget control, both
loops, ledger, setup scripts, systemd units, docs, 31 tests. 0.1.0 was the
scaffold only.

## What went well

- **The design question got settled before any code was written.** The obvious
  implementation (FTPS over the LAN) is a fraction of the code, and it was
  rejected for a reason that has nothing to do with code: Bambu gates FTP behind
  Developer Mode, which is mutually exclusive with the cloud. Writing the cheap
  version first and discovering that later would have wasted the work and,
  worse, might have shipped — trading Handy and remote monitoring for a storage
  chore without anyone deciding to.
- **Two premises were verified against the actual machine before building on
  them.** That the P2S has a USB-A host port at all (it does; the P1S/X1C
  generation does not, and carrying that assumption over would have killed the
  idea on the spot), and that it can be told to write timelapses to that drive
  rather than internal storage. The second is load-bearing: if timelapses went
  internal-only, the whole gadget would drain an empty bucket.
- **Splitting drain from ship fell out of a concrete number.** A 300 MB
  timelapse over Wi-Fi is minutes; over local disk it is seconds. Since the
  printer has no storage for the duration of a drain pass, that difference is
  the architecture.

## What was hard to understand

- **`fnmatch` does not mean what a `.gitignore` habit suggests.** `**/*.mp4`
  reads as "any .mp4 anywhere" and does not match a bare `a.mp4` in the root of
  the stick, because fnmatch needs the slash to be literally present. The
  printer very plausibly writes to the root. The drainer would have run
  forever, reported success, and moved nothing — the worst possible failure
  shape for this project. Only a test caught it.
- **The safety argument lives across three files.** The eject is in
  `gadget.py`, the mount is in `imagefs.py`, and the ordering that makes them
  safe is in `drain.py`. Reading any one of them does not tell you why the
  ordering matters, which is why the invariant is written out in
  `ARCHITECTURE.md` rather than left as a comment.
- **The idle-signal problem looked circular at first.** Knowing when the printer
  is done writing seemed to need MQTT, which needs LAN mode, which is what the
  design exists to avoid. The backing image's mtime resolves it, but only once
  you know the gadget driver writes through with ordinary VFS calls.

## Follow-ups landed in this milestone

- Root-level glob matching, with a regression test naming why it matters.
- `guards.conf` repointed and the PATCH-bump challenge switched on — both were
  guards that would have silently passed forever.
- The ship-path test rewritten to assert the actual invariant (one shell
  argument) rather than the absence of a substring.
- `make changelog-archive` and `make guards` now exist. The guards shipped with
  error messages telling you to run a target this project never had.

## Follow-ups blocked (and why)

- **Active alerting.** The failure this project dies of is silent: the drain
  loop stops, staging fills, and the first symptom is the printer refusing to
  print weeks later. `status.json` and `staging_pct` exist so something can
  watch, but nothing pushes yet. RIA is the obvious consumer and the wiring
  should wait until the Pi is running and the status shape has settled.
- **The 4 GB question.** exFAT is the default and has no per-file limit, but
  whether the P2S mounts exFAT can only be answered by the printer. If it turns
  out to be FAT32-only, an oversized timelapse is truncated by the printer
  before this code ever sees the file, and nothing here can recover it.
- **Hardware paths.** Everything touching configfs or `mount` needs a Pi wired
  to the printer. This is why `doctor` and `--dry-run` were built before the
  first run rather than after the first failure.
