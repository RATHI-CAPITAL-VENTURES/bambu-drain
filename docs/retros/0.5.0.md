# Retro — 0.5.0, a physical signal for print boundaries (2026-09-03)

**Scope:** `feat/short-segment-boundary`. Detecting the end of a print from the
size of a chamber segment, plus the fixes that made it actually work.

## What went well

- **The signal was in data we already had.** Two prints run back to back had
  merged into one folder, and the fix did not need a new source — the ledger
  already held 61 segment sizes. Printing them next to their modal value made
  the answer obvious in one glance: every full segment 100%, every ending
  12–91%, nothing between 92% and 99%.
- **It is physical, not inferential.** Time gaps and the timelapse are both
  proxies for "a print ended". A short segment *is* the recording stopping. That
  is why a 95% threshold is safe rather than tuned — it sits in a gap seven
  points wide with no observations in it.
- **Self-calibrating beat configurable.** The rotation size is a property of the
  printer and firmware. Asking the user for it would have been one more thing to
  get wrong on a new install; taking the median of what we have already archived
  costs nothing and cannot drift.

## What was hard to understand

- **The obvious statistic was the wrong one.** `modal_size` grouped by exact byte
  count and returned `None` for 61 segments, because real ones differ by a few
  kilobytes — 240.2, 240.3, 240.4 MB — and no exact value ever repeated. It did
  not error; it silently disabled the entire feature. The median is both correct
  and robust to the short segments being measured against, which the mode never
  was.
- **The right threshold was not the conservative one.** Starting at 80% felt
  safe. But the borderline case — a 218.5 MB segment at 91% — turned out to be a
  genuine print ending too, meaning the "4-hour print" was actually two runs and
  an earlier grouping had been wrong. Being *less* conservative was more correct,
  which only became visible once every segment was tabulated against the modal.

## Follow-ups landed in this milestone

- Boundary detection now works without a timelapse ever reaching the drive,
  which is the common case on this printer.
- Deploys assert resolved config values. Twice in two days a feature shipped as
  code with a config that predated it, loaded cleanly, and did nothing.

## Follow-ups blocked (and why)

- **Naming prints after their model.** The sliced `.gcode.3mf` arrives ~15
  minutes before a print's first segment, so it is both a name and a start
  marker. But the filename is the process preset — `0.2mm layer, 2 walls, 15%
  infill` — whenever the Studio project is unnamed, and the mesh objects are
  stripped from a sliced 3MF so there is no name inside it either. Usable with a
  fallback heuristic; not yet designed.
