# Retro — 0.7.0, rebuilding timelapses on the Pi (2026-09-03)

**Scope:** `feat/render-on-pi`. The ship loop rebuilds a missing timelapse from
chamber footage before that footage is shipped and deleted.

## What went well

- **The right machine was the obvious one once stated.** The first version of
  this tool ran on the Mac, and both times it was used the segments had been
  evicted to iCloud and had to be pulled back — 5 GB, minutes of waiting, and an
  `ffprobe` that hangs rather than fails on a placeholder. The footage is on the
  Pi already, for a few minutes, right before it is deleted. Rendering there
  costs no transfer at all.
- **Measuring first changed the design.** A Pi 4 doing a full decode of a
  4.4-hour print would take 103 minutes. Decoding only keyframes takes 23. That
  was not a micro-optimisation — at 103 minutes this feature would have been
  unreasonable to run automatically, and at 23 it is unremarkable. The number
  came from benchmarking one real segment on the actual hardware before any of
  the surrounding code existed.
- **The selection rule wrote itself as three conditions**, each of which
  corresponds to a way of being wrong: rendering a print that is still running,
  rendering one whose footage is already gone, and overwriting a timelapse the
  printer did produce.

## What was hard to understand

- **Keyframe density is the fact that makes this work, and it had to be
  measured.** The segments carry ~774 keyframes per 750 s — roughly one per
  second. If it had been one per ten seconds, a 60-second timelapse of a
  4-hour print would have been impossible from keyframes alone and the whole
  approach would have needed a full decode.
- **Ordering against the ship loop is load-bearing.** Rendering has to happen
  before shipping, because shipping is what deletes the raw material. Putting it
  anywhere else in the loop produces a feature that works in testing and never
  fires in production.

## Follow-ups landed in this milestone

- Rendering happens where the data already is, which removed an entire class of
  iCloud eviction problems rather than working around them.

## Follow-ups blocked (and why)

- **The existing backlog.** Four prints predate this feature and their footage
  has already shipped. `tools/make_timelapse.py` still handles them from the
  Mac; it is the same job with a download in front of it.
- **Reporting renders.** A failed render leaves the archive exactly as it would
  have been without the feature, so it is not an actionable alert. Adding it to
  the health verdict now would be noise; the case for it is evidence that
  renders fail, and there is none yet.
